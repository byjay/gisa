# GISACLUB 원격 서비스 차단 설계

## 목표

운영자가 인증된 관리자 화면에서 서비스 상태를 끄면, 이미 설치된 정상 앱도 서버 기능과 앱 UI를 잠그고 업데이트 확인·실행을 중단한다. 다시 켜면 앱은 재확인 뒤 기능을 복구한다.

## 현재 코드에서 확인한 연결점

- Worker 엔트리: `backend/cloudflare/src/index.js:31-95`; 공개 `/v1/health`, `/v1/app/version`, 관리자 라우트, 세션 보호 API가 한 `fetch` 핸들러에 있다.
- 관리자 권한: `backend/cloudflare/src/admin.js:87-220`; Cloudflare Access JWT와 서버 발급 앱 토큰을 검증한다.
- 앱 시작/화면: `lib/main.dart:34-182`; 부트스트랩 이후 `_RootGate`가 온보딩·로그인·자격증 카탈로그 화면을 연다.
- 업데이트 확인: `lib/services/app_update_service.dart:33-115`; 공개 버전 매니페스트를 읽고 URL을 연다.
- 자료 요청·메모리 캐시 세대: `lib/services/remote_content_api.dart:17-70`; `_get`/`_post`가 지연 응답을 감지한다.
- 학습 자료의 메모리 캐시 무효화: `lib/services/study_data.dart:1013-1039`.
- 설정 저장소: Worker `SETTINGS` KV는 현재 버전 매니페스트용이며, 즉시 차단 판단에 재사용하지 않는다.

## 선택한 구조

별도 Cloudflare Durable Object `ServiceControl`을 전역 단일 제어점으로 둔다. Workers KV는 공식 문서상 변경 전파가 다른 지역에 60초 이상 늦어질 수 있어 이 즉시 차단 경계에는 사용하지 않는다. Worker는 모든 데이터/인증/결제/AI/진도 라우트 실행 전과 응답 반환 직전에 상태를 확인한다. 차단 중에는 공개 상태 조회, 헬스, 관리자 토큰 검증/발급, 관리자 서비스 제어, 로그아웃만 예외로 허용한다. 버전 매니페스트와 업데이트 파일 요청은 차단한다.

앱은 `/v1/app/service-status`에서 상태를 확인하고 15초 간격으로 새로 조회한다. 상태가 꺼졌다는 응답 또는 제어 상태를 확인할 수 없는 만료 상태면 모든 화면을 유지보수 게이트로 덮고 진행 중인 원격 응답/학습 메모리 캐시를 폐기한다. 서버 `service_disabled` 응답도 즉시 전역 잠금에 반영한다. 확인되지 않은 상태에서는 기능을 열지 않는다. 관리자 화면은 유지보수 화면에서 별도로 열 수 있고 기존 서버 발급 관리자 토큰으로 제어 API를 사용한다.

관리자 계약:

- `GET /v1/app/service-status` → `{ enabled: boolean, message: string, updatedAt: string, revision: integer }`
- `GET /v1/admin/service-control` → 같은 상태 객체; 관리자 인증 필요
- `PUT /v1/admin/service-control` 입력 `{ enabled: boolean, message: string }`; 관리자 인증 필요, 저장된 상태 반환
- 제어 저장소 초기값은 `enabled: true`, 빈 메시지, revision `0`이다.
- 잘못된 저장값/제어 저장소 장애는 일반 앱 API에 대해 fail-closed `503`으로 처리한다.

## 보안·정확성 경계

- 앱 화면 차단은 정식 앱의 UX 강제다. 서버는 콘텐츠/API 접근을 별도로 거부한다.
- 정상 온라인 차단은 서버 제어 API의 쓰기 선형화 이후 새 요청부터 적용한다. 이미 선형화 전에 시작한 요청의 응답은 응답 직전 재확인으로 가능한 범위에서 차단한다. 완전히 취소할 수 없는 외부 AI/결제 작업은 제어 상태를 확인한 뒤에도 이미 실행된 부작용이 취소된다고 보장하지 않는다.
- Durable Object의 단일 객체는 현재 서비스 요청량이 작다는 가정의 설계 선택이다. 부하가 증가하면 관측 후 용량/요청 경로를 재평가한다.
- 로컬 사용자 진도/개인 설정은 삭제하지 않는다. 잠금 화면에서는 접근하지 않는다.
- 기기 네트워크가 완전히 단절되면 앱은 확인된 상태를 최대 45초까지만 유효하게 보고, 이후 잠금/재시도 화면으로 전환한다.
- 이미 다른 곳에 복사된 APK/직접 APK URL, 변조된 클라이언트, 추출된 캐시 자료를 원격으로 회수할 수는 없다. 운영 다운로드 저장소 자체는 이 구현에서 제거하지 않는다.
- 배포는 범위 밖이다. Durable Object migration이 포함된 Worker 배포 전까지 원격 차단은 실제 운영 서버에 적용되지 않는다.

## 성공 조건

1. Worker가 꺼진 상태에서 인증 전·후 데이터 라우트, 버전 API, 결제/AI/진도 접근을 `503 service_disabled`로 막는다.
2. 관리자 인증 없이 상태 변경이 불가능하고, 인증된 관리자는 꺼짐/켜짐을 왕복한다.
3. 앱 시작 때 상태 미확인·꺼짐이면 학습/로그인/업데이트 화면을 노출하지 않는다.
4. 이미 표시 중인 앱도 15초 poll 또는 `503 service_disabled` 수신 뒤 잠금 상태로 바뀐다.
5. 토글 뒤 지연된 응답은 세대 검사로 메모리 캐시에 다시 들어오지 않는다.
6. 모든 격리 테스트와 TLA+ 유한 상태 모델/의도적 결함 반례를 재현 가능하게 남긴다.

## 제한

서버 원격 제어는 배포 및 앱의 네트워크 상태에 의존한다. 앱스토어의 설치 파일, 서버가 아닌 URL에 이미 캐시된 배포 파일, 변조된 바이너리 자체를 삭제하거나 비활성화하는 DRM 기능은 아니다.
